# 五个界限上下文与三个微服务

## 逻辑边界

博客系统按领域模型划分为五个界限上下文：

| 上下文 | 主要职责 | 主要聚合/模型 |
| --- | --- | --- |
| User | 用户身份、认证、会话、资料 | `User`、`Session` |
| Article | 文章生命周期、公开内容、图片资源、浏览统计与热榜查询投影 | `Article`、`ViewHistory`、`HotRankItem` |
| Comment | 评论、回复、评论权限与评论统计 | `Comment` |
| Like | 文章点赞、评论点赞、点赞状态与点赞事件 | `Like`/点赞关系 |
| Notification | 通知、通知内容快照、已读/未读 | `Notification` |

五个上下文拥有自己的领域模型和 Port。上下文之间不得共享聚合实体或直接调用对方 Repository。浏览统计属于 Article 上下文的文章查询能力；热榜属于 Article 上下文的读模型，不代表 Article 聚合必须持有热榜数据。

## 物理部署

逻辑边界不等于进程边界，当前仍部署三个微服务：

```text
Identity Service  -> User
Content Service   -> Article
Community Service -> Comment + Like + Notification
```

同一微服务内的上下文也通过公开的应用接口、查询 Port 或事件协作，不能因为运行在同一进程就直接访问彼此的内部实现。

## 通信规则

- 目标存在性、权限和可互动性判断使用带超时的同步查询 Port。
- 点赞完成后的通知、统计和排行更新使用版本化事件，允许最终一致。
- 通知消费使用事件 ID 幂等；通知失败不回滚已经成功的点赞或评论。
- 事件至少包含 `event_id`、`version`、事件类型、业务主键和发生时间。

## 读模型

读模型只在查询目标明确时引入，不等同于所有查询都必须做读写分离：

- 热榜使用独立排行投影。
- 高频互动摘要可以使用统计投影。
- 普通文章、评论和点赞状态查询先使用查询 Port，不强制复制数据。

读模型通过可重放事件更新，允许短暂最终一致，并支持去重与重建；它不改变各上下文的写入所有权。
