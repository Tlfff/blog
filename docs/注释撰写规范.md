# Go 注释撰写规范

## 1. 目的

本文用于统一本项目 Go 代码的注释风格，使代码的业务含义、处理流程和关键约束清晰可读，降低维护和交接成本。

本规范重点约束以下内容：

- 结构体及其字段注释；
- 函数和方法的函数头注释；
- 函数或方法体内的流程注释；
- 参数较多时的参数说明。

除非特别说明，新增代码和修改代码均应遵守本规范。

## 2. 通用要求

1. 注释优先使用中文，表达应简洁、准确、易懂。
2. 注释应说明代码的业务含义、处理目的或关键约束，不能只重复代码字面含义。
3. 注释应紧挨被说明的代码，避免注释与代码相距过远。
4. 函数体内的流程注释使用阿拉伯数字编号，从 `1` 开始，按实际执行顺序递增。
5. 流程存在分支或初始化子步骤时，可以使用二级编号，例如 `1.1`、`1.2`，但最多只能到二级编号，禁止使用 `1.1.1` 及更深层级。
6. 注释中的专有名词、错误信息、配置项名称、数据库字段名和接口字段名，应尽量与代码中的实际名称保持一致。
7. 注释应随代码逻辑同步维护。修改逻辑后，必须检查相关注释是否仍然准确。
8. 不添加无实际价值的注释，例如“定义变量”“调用函数”“返回结果”等明显重复代码含义的描述。
9. 注释行不宜过长；较长说明应拆成多行，但同一语义应保持完整。
10. 代码格式统一使用 `gofmt`，字段行尾注释的对齐以格式化后的代码为准，不手工追求固定空格数量。

## 3. 结构体及字段注释规范

### 3.1 基本要求

1. 结构体中的每个字段都必须添加对应注释。
2. 字段注释统一写在字段定义行末尾，使用 `//` 开始。
3. 字段注释应说明字段的业务含义；必要时补充取值范围、状态含义、单位或特殊约束。
4. 数据库模型字段应优先说明业务含义，不只照抄 `gorm` 标签中的字段名。
5. 状态、类型、枚举等字段必须标明各取值的含义。
6. 时间字段应明确表示创建时间、更新时间、删除时间或其他具体时间含义。
7. 保持字段定义、标签和注释的顺序一致，不要为了注释调整结构体字段顺序。

### 3.2 示例

```go
type ArticleLike struct {
	ID          uint64    `gorm:"column:id;primaryKey;autoIncrement"` // 唯一标识
	UserID      uint64    `gorm:"column:user_id"`                     // 用户ID
	ArticleID   uint64    `gorm:"column:article_id"`                  // 文章ID
	Status      int8      `gorm:"column:status"`                      // 点赞状态：1-点赞；2-取消点赞
	CreatedTime time.Time `gorm:"column:created_time;autoCreateTime"` // 创建时间
	UpdatedTime time.Time `gorm:"column:updated_time;autoUpdateTime"` // 最后更新时间
}
```

### 3.3 特殊情况

- 匿名字段或嵌入字段也必须说明其用途，例如：

  ```go
  type ArticleResponse struct {
  	BaseResponse // 通用响应字段
  	Article      *Article `json:"article"` // 文章详情
  }
  ```

- 字段注释必须保持在对应字段的行尾。字段定义较长时，可以通过合理缩短标签、类型别名或字段命名改善可读性，但不能将字段说明移到其他位置。
- 对外暴露的结构体，除字段行尾注释外，建议补充结构体整体用途注释，并以结构体名称开头，符合 Go 文档注释习惯：

  ```go
  // ArticleLike 表示用户对文章的点赞记录。
  type ArticleLike struct {
  	ID uint64 `gorm:"column:id;primaryKey;autoIncrement"` // 唯一标识
  }
  ```

## 4. 函数和方法注释规范

### 4.1 函数头注释

1. 每个函数或方法都应在函数声明前添加一行功能注释。
2. 功能注释应简要说明函数或方法“做什么”，优先使用动宾结构，例如“获取文章图片上传凭证”“初始化数据库连接”。
3. 函数头注释与函数声明之间不能插入无关代码或空白逻辑。
4. 对外导出的函数或方法，函数头注释应以函数名或方法名开头，并继续说明其功能；例如 `// GetImageUploadURL 获取文章图片上传凭证。`。未导出的内部函数可以直接写功能说明，但优先保持同样的清晰风格。
5. 函数头注释不描述函数体内的全部实现细节，详细执行顺序放在函数体内通过编号说明。

### 4.2 函数体内的流程注释

1. 按处理顺序使用一级编号：`1.`、`2.`、`3.`。
2. 一级编号应对应一个完整的业务阶段或处理步骤，不要为每一行代码都添加编号。
3. 一个一级步骤包含多个有必要说明的子步骤时，使用二级编号：`1.1`、`1.2`。
4. 编号最多到二级，禁止出现 `1.1.1`、`2.1.1` 等三级及更深编号。
5. 流程注释放在对应代码块之前，说明下面代码块要完成的动作。
6. 失败处理、提前返回、资源释放等关键行为应在附近补充说明；如果只是直观的错误返回，不需要重复代码含义。
7. `defer`、事务提交或回滚、权限校验、数据转换等容易影响执行顺序或结果的逻辑，应在必要时说明其目的。
8. 同一层级的编号应连续、清晰，不因某个步骤没有注释而随意跳号。
9. 函数体较短但包含多个业务动作时，仍应按业务流程添加编号。仅包含单个简单动作的函数可以只写 `// 1. ...`，不应为了凑数量虚构多个步骤。

### 4.3 函数注释示例

```go
// GetImageUploadURL 获取文章图片上传凭证。
func (h *ArticleHandler) GetImageUploadURL(c *gin.Context) {
	// 1. 解析请求体并放进 req
	var req articleDTO.GetImageUploadURLRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		c.Error(common.ErrInvalidRequestBody)
		return
	}

	// 2. 获取凭证
	uploadURL, url, err := h.image.GetUploadURL(c, req.FileExt)
	if err != nil {
		c.Error(err)
		return
	}

	// 3. 返回凭证
	common.OK(c, "获取成功", gin.H{
		"upload_url": uploadURL,
		"url":        url,
	})
}
```

> 说明：示例中的包名采用常规 Go 命名形式 `articleDTO`。实际编写时应以项目中已经存在的包名为准，不因注释规范擅自修改业务代码。

## 5. 复杂初始化函数的注释规范

当函数包含多个初始化阶段时，可以先使用一级编号表示主要阶段，再使用二级编号表示阶段内的子步骤。每个阶段的编号应反映真实执行流程。

```go
// Run 启动博客系统后端服务并完成运行环境初始化。
func Run(cmd *cobra.Command, args []string) {
	fmt.Printf("博客系统后端服务正在启动,监听窗口：%s...\n", port)

	// 1. 加载配置并初始化基础工具
	config, err := config.LoadConfig("config/config.yaml")
	if err != nil {
		fmt.Printf("[error]:加载配置文件失败：%v\n", err)
		return
	}

	// 1.1 初始化自定义验证器
	common.InitValidator()

	// 1.2 初始化 IP 工具类
	dir, _ := os.Getwd() // 获取当前程序运行的绝对路径
	dbPath := filepath.Join(dir, "pkg/resource/ip2region.xdb")
	if err := iputil.InitIPSearcher(dbPath); err != nil {
		log.Fatalf("[error]:初始化 IP 解析器失败: %v", err)
	}

	// 在程序退出时释放内存
	defer iputil.Close()

	// 2. 初始化数据库连接
	// 2.1 初始化 MySQL
	db, err := database.NewMySQLClient(
		config.Database.Username,
		config.Database.Password,
		config.Database.Host,
		config.Database.Port,
		config.Database.DBName,
	)
	if err != nil {
		fmt.Printf("[error]:数据库连接初始化失败：%v\n", err)
		return // 连接失败必须立刻拦截并退出，不能继续向下传递 nil
	}

	// 2.2 初始化 MongoDB
	mongodb, err := database.NewMongoDBClient(
		config.Mongodb.Username,
		config.Mongodb.Password,
		config.Mongodb.Host,
		config.Mongodb.DBName,
		config.Mongodb.Port,
	)
	if err != nil {
		fmt.Printf("[error]:MongoDB 连接初始化失败：%v\n", err)
		return
	}

	// 3. 启动服务
	_ = db
	_ = mongodb
}
```

### 5.1 说明

- `1.`、`2.`、`3.` 表示主要流程阶段。
- `1.1`、`1.2`、`2.1`、`2.2` 表示对应阶段的子步骤。
- “在程序退出时释放内存”属于资源生命周期说明，不需要强行写成 `1.3`，避免让编号变成对每一行代码的机械标记。
- 关键的错误拦截原因可以写在 `return` 行尾，但不要对所有普通 `return` 都重复说明。

## 6. 参数较多时的注释规范

### 6.1 触发条件

函数或方法传入参数数量**大于等于 5 个**时，除功能说明外，函数头注释中必须增加参数说明。

参数数量按函数声明中的实际参数计算；接收者不计入参数数量。例如：

```go
func (s *ArticleService) CreateArticle(
	ctx context.Context,
	authorID uint64,
	title string,
	content string,
	coverURL string,
	status int8,
) error
```

该方法有 6 个传入参数，因此必须补充参数说明。

### 6.2 参数说明格式

1. 在功能注释之后增加“参数说明：”。
2. 每个参数单独占一行。
3. 参数名、含义和必要的约束应写清楚。
4. 参数说明的顺序应与函数声明中的参数顺序一致。
5. 不需要为返回值添加冗长说明；只有在返回值含义不直观或存在特殊约束时才补充。

```go
// CreateArticle 创建文章。
//
// 参数说明：
//   - ctx：请求上下文，用于传递链路信息和控制超时。
//   - authorID：作者唯一标识。
//   - title：文章标题，不能为空。
//   - content：文章正文内容。
//   - coverURL：文章封面地址，可以为空。
//   - status：文章状态：1-草稿；2-已发布。
func (s *ArticleService) CreateArticle(
	ctx context.Context,
	authorID uint64,
	title string,
	content string,
	coverURL string,
	status int8,
) error {
	// 1. 校验文章参数
	if title == "" {
		return errors.New("文章标题不能为空")
	}

	// 2. 组装文章数据
	article := &Article{
		AuthorID: authorID,
		Title:    title,
		Content:  content,
		CoverURL: coverURL,
		Status:   status,
	}

	// 3. 保存文章
	return s.articleRepo.Create(ctx, article)
}
```

### 6.3 参数说明的例外

- 参数少于 5 个时，不强制增加参数列表；参数含义非常规或容易误用时，可以主动补充。
- 如果参数过多导致函数难以理解，应优先评估是否可以改为传入请求结构体或配置结构体；参数说明不能替代合理的接口设计。
- 使用 `context.Context` 时，应说明其用途，但不需要解释 Go 标准库的基础概念。

## 7. 其他代码元素的注释建议

以下内容虽然不属于本规范的强制重点，但建议统一遵守：

### 7.1 包注释

对外提供能力的包建议添加包注释，说明包的职责和边界。包注释应放在包声明附近，并以包名开头。

```go
// article 提供文章发布、查询和管理相关能力。
package article
```

### 7.2 接口注释

接口注释说明接口整体职责；接口中的方法仍需按照函数注释规范添加方法说明。

```go
// ArticleRepository 定义文章数据访问能力。
type ArticleRepository interface {
	// 根据唯一标识查询文章。
	FindByID(ctx context.Context, id uint64) (*Article, error)
}
```

### 7.3 常量和枚举

常量组中的每个对外暴露常量都应说明含义；状态值应明确列出取值含义。

```go
const (
	ArticleStatusDraft     int8 = 1 // 草稿
	ArticleStatusPublished int8 = 2 // 已发布
)
```

### 7.4 关键业务规则

权限校验、幂等处理、事务边界、缓存失效、软删除、兼容旧数据等不易从代码直接看出的规则，应在相关代码块前补充说明。

## 8. 不推荐的写法

### 8.1 不推荐：字段没有逐一说明

```go
type Article struct {
	ID        uint64
	AuthorID  uint64
	Status    int8
}
```

应改为：

```go
type Article struct {
	ID       uint64 `gorm:"column:id"`        // 唯一标识
	AuthorID uint64 `gorm:"column:author_id"` // 作者唯一标识
	Status   int8   `gorm:"column:status"`    // 文章状态：1-草稿；2-已发布
}
```

### 8.2 不推荐：只写函数名或实现细节

```go
// CreateArticle
// 创建 Article 对象，调用 repo.Create，然后返回错误。
func (s *ArticleService) CreateArticle(...) error {
	// 调用 repo.Create
	return s.articleRepo.Create(...)
}
```

应改为以业务功能为主，并将必要的流程说明放在函数体对应代码块之前：

```go
// CreateArticle 创建文章。
func (s *ArticleService) CreateArticle(...) error {
	// 1. 校验并组装文章数据
	// 2. 保存文章
	return s.articleRepo.Create(...)
}
```

### 8.3 不推荐：编号层级过深

```go
// 1. 初始化服务
// 1.1 初始化数据库
// 1.1.1 初始化连接池
// 1.1.1.1 设置最大连接数
```

最多保留二级编号：

```go
// 1. 初始化服务
// 1.1 初始化数据库连接
// 1.2 初始化缓存连接
```

### 8.4 不推荐：为每行代码添加注释

```go
// 声明 req
var req Request
// 绑定 JSON
if err := c.ShouldBindJSON(&req); err != nil {
	// 返回错误
	c.Error(err)
	// 结束函数
	return
}
```

应按完整动作组织注释：

```go
// 1. 解析请求体并校验请求参数
var req Request
if err := c.ShouldBindJSON(&req); err != nil {
	c.Error(err)
	return
}
```

## 9. 提交前检查清单

提交代码前，应至少检查以下内容：

- [ ] 结构体的每个字段是否都有对应注释？
- [ ] 状态、类型、枚举字段是否写明了取值含义？
- [ ] 每个函数或方法是否有简洁的函数头功能注释？
- [ ] 函数体内是否按照实际业务流程添加了 `1.`、`2.`、`3.` 注释？
- [ ] 是否只使用到二级编号，未出现 `1.1.1` 等更深层级？
- [ ] 函数参数数量大于等于 5 个时，是否逐行补充了参数说明？
- [ ] 注释是否描述业务含义和关键约束，而不是重复代码？
- [ ] 注释是否与当前实现一致？
- [ ] 是否已执行 `gofmt`，并确认字段行尾注释没有破坏代码可读性？
